현재 문서는 마일스톤 #1의 PR #22(출결), #23(팀), #24(공지), #25(과제 알림) 통합을 전제로 합니다. 미배포 화면을 운영에서 사용 가능하다고 안내하지 않습니다. 실제 서비스 URL, 현장 담당자, 지원 시간, 복구 목표는 아래 인수표에서 확정해야 합니다.

## 우선순위와 연락 기준

- **긴급**: 다른 학생/팀의 비공개 자료 노출, 데이터 유실·중복/오배정 확산, DB 손상. 관련 입력/발송을 중지하고 즉시 비상 개발자에게 알립니다. 학생 활동은 인쇄 명단·구두 안내로 이어갑니다.
- **높음**: 전체 로그인/출결 저장/과제 제출 장애, 모든 Discord 채널 접근 불가. 현장 담당자가 대체 절차를 시작하면서 비상 개발자에게 연락합니다. 임시 목표는 10분 이내 첫 응답이며 확정 SLA는 인수표에 기록합니다.
- **일반**: 일부 알림 지연·개인 인증/DM 실패. 원장 상태를 먼저 확인하고 해당 사람만 재시도합니다. 같은 원인으로 2회 실패하거나 수업 진행에 영향이 있으면 개발자를 호출합니다.

## 현장 권한과 승인 경계

현장 관리자는 자기 워크스페이스의 출결·공지·팀·과제 운영과 실패 재시도를 수행합니다. 조 멘토는 담당 범위의 출결과 팀 배정을 수행하며 회차 마감과 공지 발송은 관리자에게 요청합니다. Discord에서는 필요한 채널 확인 권한만, GitHub/Render에서는 실제 인수 시 지정한 최소 권한만 부여합니다.

운영 DB 삭제·교체·SQL 직접 변경, 채널/역할 대량 삭제, 토큰 교체, Render 서비스/디스크 이전, 마이그레이션·복원, 운영 배포·롤백은 **복구 승인자 확인 후 개발자가 수행**합니다. 이 문서는 이 작업을 미리 승인하지 않습니다. 계정 추가·회수는 [인증 운영](./AUTH-OPERATIONS.md)과 [워크스페이스](./WORKSPACES.md)를 따릅니다.

## 유지보수 담당자 절차

구성: 브라우저 → Node Web API → 워크스페이스별 SQLite가 원장을 소유합니다. 봇은 인증된 API로 저장소·역할 설정·발송 큐를 조회하고 Discord에 적용합니다. 웹 저장소 전환 이전 설치에는 봇 로컬 DB가 남을 수 있으므로 [BOT-DATA.md](./BOT-DATA.md)의 이관 상태를 먼저 확인합니다.

환경변수 이름: Web의 `BOT_DB_PATH`, `ADMIN_PASSWORD`, `ALLOWED_ORIGINS`, `PYTHON_EXECUTABLE`, `LEARNINGOPS_PROVISION_TOKEN`, `LEARNINGOPS_AUTH_TOKEN`; 봇의 `DISCORD_TOKEN`, `DB_PATH`, `LEARNINGOPS_PROVISION_URL/TOKEN`, `LEARNINGOPS_AUTH_URL/TOKEN`. 비밀값은 서비스 환경변수 또는 승인된 비밀 저장소에서만 관리하며 문서·이슈·대화에 복사하지 않습니다. 현재 Blueprint의 봇 명칭은 `ax-mentoring-bot`이며 실제 서비스/디스크 연결은 인수표에 기록합니다.

재시작: 수동 대체 준비 → 진행 중 저장·발송과 큐 상태 기록 → 개발자가 기존 서비스 인스턴스 재시작 → health/로그인 → 봇 연결 → 명단·제출·발송 결과 대사. 동일 토큰을 쓰는 봇 복제본을 동시에 실행하지 않습니다. 새 빈 DB를 기존 DB 대신 연결하지 않습니다. lease가 끝난 불확실한 발송은 자동 조회/보류 정책으로 복구합니다.

배포: CI 통과와 백업 검증 → 수업 외 작업 시간/승인 → Git Flow release 검토 → 기존 Web 서비스에 Web/Python 코드 배포 → 기존 봇 서비스 배포 → health, 로그인, 각 기능 1건, private 채널 권한 확인. main push는 Pages 자동 배포를 시작하므로 마일스톤 PR 완료만으로 main에 병합하지 않습니다.

롤백: 인증 불가·저장 실패·정보 노출·전송 중복 등 회귀가 있으면 수동 대체 및 전송 중지 후 승인자에게 요청합니다. 추가된 큐/회차 테이블이 있는 상태에서 구버전 코드를 바로 실행하지 않습니다. 특히 구버전 학생 조회는 미마감 출결을 공개할 수 있고 과거 D-1 루프는 중복 알림을 보낼 수 있습니다. 먼저 관련 화면/봇 전송을 차단하고 호환성 검증한 수정 배포를 우선 검토합니다. DB 복원은 새로 저장된 운영 데이터 손실을 동반하므로 별도 승인·대사 후 진행합니다.

## 백업과 복구 훈련

제안 주기: 매 수업 전과 매일, 보존 14일, 배포 전 별도 보관. 실제 주기·보존·RPO/RTO는 승인자가 인수표에서 확정합니다. 자동 스케줄은 운영 계정의 cron/스케줄러에서 아래 `backup`과 `verify` 명령을 날짜별 **새 경로**로 실행하도록 등록하고 실패 알림 담당자를 지정합니다. 이 PR은 운영 스케줄러를 변경하지 않습니다. 자동 삭제는 제공하지 않으며 승인된 보존 정책으로 별도 관리합니다.

저장 중 WAL 파일을 빠뜨리는 단순 파일 복사 대신 도구의 SQLite backup API를 사용합니다. 각 DB 파일은 일관된 스냅샷이지만 여러 DB 전체가 같은 시점이라는 보장은 없으므로 수업 입력과 봇 저장을 멈춘 유지보수 창에 실행합니다. 백업에는 계정·인증·학생 데이터가 있으므로 접근 제한 및 암호화된 외부 보관이 필요합니다.

프로젝트 루트에서 **실제 경로를 확인한 개발자**가 실행하는 예시:

```sh
python scripts/lms_backup.py backup --source /approved/path/mentoring.db --output /approved/backups/2026-09-18-before-class
python scripts/lms_backup.py verify --backup /approved/backups/2026-09-18-before-class
python scripts/lms_backup.py restore --backup /approved/backups/2026-09-18-before-class --output /approved/rehearsal/restore-2026-09-18
```

도구는 메인 DB와 `<메인DB파일명>.workspaces/*.db`를 함께 보관하고, 마지막에 manifest·SHA-256·파일 크기를 기록합니다. manifest가 없거나 검증 실패한 디렉터리는 정상 백업으로 사용하지 않습니다. 복원은 **새 디렉터리만** 허용하며 운영 DB를 덮어쓰지 않습니다.

복구 훈련: 새 디렉터리 복원 → 별도 테스트 Web 인스턴스를 복원된 DB에 연결 → 실제 Discord로 전송되지 않도록 연동 비밀값 없이 격리 → 계정 로그인, 워크스페이스 수, 출결 회차·명단, 팀 배정, 제출 건수, outbox 대기/불확실 건수 대조 → 결과·소요시간 기록. 실제 운영 경로 전환은 추가 승인 후 수행합니다. 복원된 큐는 과거 발송 상태일 수 있으므로 봇을 연결하기 전에 이미 발송된 메시지와 반드시 대사합니다.
